# Starlight content conventions

> **New folder.** `docs/research/` did not exist before this file. The repo previously had
> `docs/adr/`, `docs/agents/`, `docs/design/` and `docs/guide/`. This folder is for research notes:
> findings gathered from external primary sources, kept so we do not have to re-derive them.

**Scope.** Conventions that a plain-Markdown folder (`docs/guide/`) must follow so that a Starlight
site living in a *separate* repo can consume it as its `docs` content collection.

**Sources.** Only the official Starlight docs (<https://starlight.astro.build>), the Astro docs
(<https://docs.astro.build>), and the `withastro/starlight` / `withastro/astro` sources. Source-code
citations are pinned to commit SHAs so the line numbers stay valid:

## Summary — what is settled

| Decision | Verdict | Detail |
| --- | --- | --- |
| `title` + `description` in frontmatter | ✅ Correct | `title` is the only required field; `description` is optional and recommended. → [§1](#1-frontmatter-schema) |
| `sidebar.order` for page ordering | ✅ Correct | Lower first; unordered pages sink to the bottom; ties broken alphabetically. → [§3](#3-autogenerated-sidebar) |
| `README.md` → `index.md` | ✅ Required | `README.md` would become the page `/readme/`. `index.md` is what maps a directory to its own URL. → [§4](#4-indexmd-inside-a-directory), [§7](#7-slugs-and-file-naming) |
| Keep `channels/` and `deployment/` | ✅ Works | Each becomes a nested sidebar subgroup automatically. → [§3](#3-autogenerated-sidebar) |
| Blockquote callouts → `:::note` asides | ✅ Works in plain `.md` | Four types only: `note`, `tip`, `caution`, `danger`. No extra config. → [§5](#5-asides-in-plain-md) |
| Plain `.md`, not `.mdx` | ✅ Fine | Asides, frontmatter, and autogenerated sidebars all work in `.md`. → [§5](#5-asides-in-plain-md) |

### Four things that need a decision, not just a convention

1. **Subgroup labels are the raw directory name.** `channels/` renders as a group literally
   labelled `channels` (lowercase, verbatim). There is **no** way to override this from inside the
   content folder — no `_meta.json`, no `_category_.json`, no frontmatter field. It can only be
   fixed in the *site's* `astro.config.mjs`. → [§3c](#3c-how-is-a-subgroups-label-derived)
2. **Directory ordering is controllable from the content folder — but only indirectly.** A
   directory inherits the *minimum* `sidebar.order` of any page inside it, recursively. So putting
   `sidebar: { order: 30 }` on `channels/index.md` moves the whole `channels` group to weight 30.
   → [§3b](#3b-how-are-directories-subgroups-ordered)
3. **`channels/index.md` is *not* the group's landing page.** It becomes the first *child link*
   inside the `channels` group. The group heading itself is not clickable. If we want it to read as
   "Overview", we must set `sidebar: { label: Overview }` ourselves — nothing is automatic.
   → [§4](#4-indexmd-inside-a-directory)
4. **Relative `./page.md` links are not rewritten.** Astro ships no such feature. Links must be
   absolute site paths (`/channels/github/`), which do *not* work when the same Markdown is read on
   GitHub. There is no official guidance for this trade-off. → [§6](#6-internal-links)

## 1. Frontmatter schema

**Docs:** <https://starlight.astro.build/reference/frontmatter/>
**Source:** [`packages/starlight/schema.ts` L13–L113](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/schema.ts#L13-L113)

`title` is the only required field. The authoring guide states it plainly: *"Every page must include
at least a `title`."*
(<https://starlight.astro.build/guides/authoring-content/#frontmatter>)

| Field | Type | Default | Notes |
| --- | --- | --- | --- |
| `title` | `string` | — | **Required.** Rendered as the page `<h1>`, the `<title>`, and page metadata. |
| `description` | `string` | *(optional)* | Page metadata / SEO / social previews. |
| `slug` | `string` | — | Overrides the page URL slug. **See the caveat below — this one is not part of Starlight's schema.** |
| `editUrl` | `string \| boolean` | `true` | `false` disables the "Edit page" link for this page. |
| `head` | `HeadConfig[]` | `[]` | Extra `<head>` tags for this page. |
| `tableOfContents` | `false \| { minHeadingLevel?: number; maxHeadingLevel?: number }` | inherits global (`{ min: 2, max: 3 }`) | `false` hides the ToC. |
| `template` | `'doc' \| 'splash'` | `'doc'` | `'splash'` = wide layout, no sidebars. |
| `hero` | `HeroConfig` | — | Hero block; works with `template: splash`. |
| `banner` | `{ content: string }` | — | Announcement banner; `content` supports HTML. |
| `lastUpdated` | `Date \| boolean` | — | Overrides the global setting / Git-derived date. |
| `prev` | `boolean \| string \| { link?: string; label?: string }` | inherits `pagination` | Previous-page link. |
| `next` | same as `prev` | inherits `pagination` | Next-page link. |
| `pagefind` | `boolean` | `true` | `false` excludes the page from the search index. |
| `draft` | `boolean` | `false` | `true` = dev-only; excluded from production builds. |
| `sidebar` | `SidebarConfig` | `{}` | See below. |

### `sidebar` sub-fields

Documented shape (<https://starlight.astro.build/reference/frontmatter/#sidebarconfig>):

```ts
interface SidebarConfig {
  label?: string;
  order?: number;
  hidden?: boolean;
  badge?: string | BadgeConfig;
  attrs?: Record<string, string | number | boolean | undefined>;
}
```

| Sub-field | Type | Default | Behaviour |
| --- | --- | --- | --- |
| `label` | `string` | the page `title` | Sidebar link text. |
| `order` | `number` | *(none → treated as `Number.MAX_VALUE`)* | *"Lower numbers are displayed higher up in the link group."* |
| `hidden` | `boolean` | `false` | Excludes the page from autogenerated sidebar groups. |
| `badge` | `string \| BadgeConfig` | — | String = default accent variant. Object = `{ text, variant, class }`, variants `note \| tip \| caution \| danger \| success \| default`. |
| `attrs` | `Record<string, string \| number \| boolean \| undefined>` | `{}` | HTML attributes on the sidebar `<a>`. |

The `sidebar` object itself defaults to `{}`
([`schema.ts` L65–L95](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/schema.ts#L65-L95)),
so omitting it is always safe.

Important scope limit from the sidebar guide: *"The `sidebar` frontmatter configuration is only used
for autogenerated links and docs links defined with the `slug` property. It does not apply to links
defined with the `link` property."*
(<https://starlight.astro.build/guides/sidebar/#customizing-autogenerated-links-in-frontmatter>)

### Caveat: `slug` is not in Starlight's Zod schema

`slug` is documented on the frontmatter reference page but does **not** appear in
[`StarlightFrontmatterSchema`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/schema.ts#L13-L113).
That is because it is consumed one level lower, by Astro's `glob()` loader, before Starlight's
schema runs. The Starlight docs point at Astro for it: *"Override the slug of the page. See
'Defining custom IDs' in the Astro docs for more details."*
(<https://starlight.astro.build/reference/frontmatter/#slug>)

The mechanism is literally the first two lines of Astro's default ID generator:

```ts
function generateIdDefault({ entry, base, data }: GenerateIdOptions, isLegacy?: boolean): string {
	if (data.slug) {
		return data.slug as string;
	}
```

— [`packages/astro/src/content/loaders/glob.ts` L48–L51](https://github.com/withastro/astro/blob/9865d1c03af6d1a1f15c9811858778cc952ca4e4/packages/astro/src/content/loaders/glob.ts#L48-L51)

Two consequences worth recording: (a) `slug` is not type-checked or error-mapped by Starlight, and
(b) if the site ever passes a custom `generateId()` to `docsLoader()`, `slug` frontmatter stops
working unless that function reimplements the check.

### Extending the schema

`docsSchema({ extend: … })` accepts a Zod schema (or a function returning one, for the Astro
`image()` helper) and deep-merges it into the default schema
(<https://starlight.astro.build/reference/frontmatter/#extend>). Relevant to us only as an escape
hatch: the *site* repo could make `description` required, which would then be enforced against our
folder.

## 2. H1 handling

**Docs:** <https://starlight.astro.build/guides/authoring-content/#how-to-structure-page-content-in-starlight>

> *"Starlight is configured to automatically use your page title as a top-level heading and will
> include an 'Overview' heading at top of each page's table of contents. We recommend starting each
> page with regular paragraph text content and using on-page headings from `<h2>` and down."*

Confirmed in source. The `<h1>` is rendered by a dedicated component from the frontmatter `title`:

```astro
<h1 id={PAGE_TITLE_ID}>{Astro.locals.starlightRoute.entry.data.title}</h1>
```

— [`components/PageTitle.astro` L5](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/components/PageTitle.astro#L5)
(`PAGE_TITLE_ID` is `'_top'`, see
[`constants.ts`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/constants.ts))

`<PageTitle />` is rendered for every page that does **not** declare a `hero`, independent of
`template`:
[`components/Page.astro` L98–L109](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/components/Page.astro#L98-L109).

**If the Markdown body also starts with `# H1`:** there is no code anywhere in Starlight that strips
or demotes a body-level `<h1>`. The body is rendered as-is into `<MarkdownContent>`, *after* the
`PageTitle` panel. So the page would ship **two** `<h1>` elements — the frontmatter one and the body
one. That body `<h1>` is also invisible in the table of contents, because the ToC filter defaults to
`minHeadingLevel: 2`:

```ts
const defaults = { minHeadingLevel: 2, maxHeadingLevel: 3 };
```

— [`schemas/tableOfContents.ts` L3](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/schemas/tableOfContents.ts#L3),
applied in [`utils/generateToC.ts`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/utils/generateToC.ts).

**Convention for `docs/guide/`:** every file must carry `title:` in frontmatter and must **not**
begin with an `# H1`. Body headings start at `##`. (This is exactly the transformation needed when
converting a GitHub-style `README.md`, which normally opens with an `# H1`.)

## 3. Autogenerated sidebar

**Docs:** <https://starlight.astro.build/guides/sidebar/#autogenerated-links>
**Source:** [`utils/navigation.ts`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/utils/navigation.ts)

Since **Starlight 0.39.0** the config shape is an `autogenerate` object *inside* an `items` array:

```js
starlight({
  sidebar: [
    { label: 'Constellations', items: [{ autogenerate: { directory: 'constellations' } }] },
  ],
});
```

The pre-0.39 form (`{ label, autogenerate }` at the same level) is now a hard error with a
migration message
([`schemas/sidebar.ts` L77–L102](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/schemas/sidebar.ts#L77-L102);
changelog entry for
[0.39.0 / PR #3618](https://github.com/withastro/starlight/blob/main/packages/starlight/CHANGELOG.md)).
If no `sidebar` is configured at all, Starlight autogenerates the whole sidebar from the collection
root
([`navigation.ts` L403–L414](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/utils/navigation.ts#L403-L414)).

`autogenerate.directory` refers to the **on-disk directory name**, not the sluggified URL segment;
leading/trailing slashes are stripped. Starlight's own test suite uses
`autogenerate: { directory: '/Deprecated API/' }` against a `Deprecated API/users.md` file that is
served at `/deprecated-api/users/`
([`__tests__/sidebar/vitest.config.ts`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/__tests__/sidebar/vitest.config.ts),
[`schemas/sidebar.ts` L66](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/schemas/sidebar.ts#L66)).

Pages with `sidebar.hidden: true` are filtered out before the tree is built
([`navigation.ts` L244](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/utils/navigation.ts#L244)),
and `draft: true` pages are *"automatically excluded in production builds"*
(<https://starlight.astro.build/reference/frontmatter/#draft>).

### 3a. How are pages ordered within a group?

The published docs say only: *"By default, pages are sorted in alphabetical order according to the
file `id`."* (<https://starlight.astro.build/guides/sidebar/#autogenerated-links>) and *"Lower
numbers are displayed higher up in the link group."*
(<https://starlight.astro.build/reference/frontmatter/#order>). The docs do **not** state the
tie-breaking rule or what happens to pages with no `order`. The source does:

```ts
/**
 * Get the sort weight for a given route or directory. Lower numbers rank higher.
 * Directories have the weight of the lowest weighted route they contain.
 */
function getOrder(routeOrDir: Route | Dir): number {
	return isDir(routeOrDir)
		? Math.min(...Object.values(routeOrDir).flatMap(getOrder))
		: // If no order value is found, set it to the largest number possible.
			(routeOrDir.entry.data.sidebar.order ?? Number.MAX_VALUE);
}

/** Sort a directory’s entries by user-specified order or alphabetically if no order specified. */
function sortDirEntries(dir: [string, Dir | Route][]): [string, Dir | Route][] {
	const collator = new Intl.Collator(localeToLang(undefined));
	return dir.sort(([_keyA, a], [_keyB, b]) => {
		const [aOrder, bOrder] = [getOrder(a), getOrder(b)];
		// Pages are sorted by order in ascending order.
		if (aOrder !== bOrder) return aOrder < bOrder ? -1 : 1;
		// If two pages have the same order value they will be sorted by their slug.
		return collator.compare(isDir(a) ? a[SlugKey] : a.id, isDir(b) ? b[SlugKey] : b.id);
	});
}
```

— [`utils/navigation.ts` L292–L313](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/utils/navigation.ts#L292-L313)

Exact rules:

1. A page's weight is `sidebar.order`, or `Number.MAX_VALUE` if absent.
2. Entries are sorted by weight **ascending**.
3. Pages **without** `order` therefore all share `Number.MAX_VALUE` and sink below every ordered
   page — they are not interleaved.
4. **Ties** (same weight, including the common "nobody set `order`" case) are broken by
   `Intl.Collator(<default locale lang>).compare()` — i.e. locale-aware alphabetical, not raw
   `String` comparison — on the entry `id` (the sluggified path, lowercase) for pages.
5. `Array.prototype.sort` is used, which is stable per spec, but the comparator is total here so
   stability does not matter in practice.

The same rule is spelled out in the schema doc-comment: *"Pages are sorted by this value in
ascending order. Then by slug. If not provided, pages will be sorted alphabetically by slug. If two
pages have the same order value, they will be sorted alphabetically by slug."*
([`schema.ts` L67–L72](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/schema.ts#L67-L72))

**Practical consequence for `docs/guide/`:** either give *every* page an explicit `sidebar.order`, or
none of them. A partial set produces "ordered pages first, then everything else alphabetically",
which is rarely what anyone means.

### 3b. How are directories (subgroups) ordered?

Two facts, both from `getOrder` / `sortDirEntries` above:

- **Directories and pages are sorted in one single list.** There is no "directories first" or
  "directories last" bucketing — `sortDirEntries` receives `Object.entries(dir)` containing both
  kinds and sorts them together
  ([`navigation.ts` L327–L340](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/utils/navigation.ts#L327-L340)).
- **A directory's weight is the minimum weight of everything it contains, recursively**
  (`Math.min(...Object.values(routeOrDir).flatMap(getOrder))`).

This answers the "can a directory's position be controlled from the content folder?" question:
**yes, indirectly.** Setting `sidebar: { order: 30 }` on any single page inside `channels/` — most
naturally `channels/index.md` — gives the whole `channels` subgroup a weight of 30 and positions it
accordingly among its siblings. A directory containing no ordered pages gets `Number.MAX_VALUE` and
falls back to alphabetical placement.

This is verifiable in the shipped snapshot test: inside the `Reference` group, the page
`reference/configuration.mdx` sorts *before* the `frontmatter` subgroup, because
`'reference/configuration'` collates before `'reference/frontmatter'` — a page and a directory
interleaved by name alone
([`__tests__/sidebar/navigation.test.ts`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/__tests__/sidebar/navigation.test.ts)).

**Per-directory config file: none exists.** There is no `_meta.json`, `_category_.json`,
`.order`, or equivalent. `groupFromDir` reads nothing from the filesystem — it only walks the
in-memory tree built from the loaded entries
([`navigation.ts` L327–L340](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/utils/navigation.ts#L327-L340)).
A GitHub code search across `packages/starlight` for `_meta` and `_category_` returns nothing. Note
also that the loader glob ignores any file starting with `_`
([`loaders.ts` L57](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/loaders.ts#L57)),
so such a file would not even be loaded.

> ⚠️ **Subtle inconsistency in the tie-break key.** For pages the comparison key is `a.id` — the
> *sluggified* path (lowercased, `github-slugger`-processed). For directories it is `a[SlugKey]` —
> the *raw on-disk* path, unsluggified. So a directory named `Deployment/` compares as
> `"Deployment"` while a sibling page compares as `"deployment-notes"`. `Intl.Collator` mostly
> papers over this (it is not a naïve byte comparison), but it is a real asymmetry. It does not
> affect us: `channels/` and `deployment/` are already lowercase, ASCII, space-free. Keep it that
> way.

### 3c. How is a subgroup's label derived?

**Verbatim, from the directory name on disk — no transformation, no title-casing, no lookup:**

```ts
return {
	type: 'group',
	label: dirName,
	entries,
	…
};
```

— [`navigation.ts` L327–L340](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/utils/navigation.ts#L327-L340)

The published docs show this implicitly: a `seasonal/` directory renders as a group labelled
lowercase `seasonal`, sitting next to title-cased page labels
(<https://starlight.astro.build/guides/sidebar/#autogenerated-links>). Starlight's own tests assert
group labels of `"guides"` and `"Getting Started"` — exactly the directory names
([`__tests__/basics/navigation.test.ts`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/__tests__/basics/navigation.test.ts)).

**It cannot be customised from within the content folder.** There is no frontmatter field, no
sidecar file, nothing. The only ways to get `Channels` instead of `channels` are, all in the *site*
repo's `astro.config.mjs`:

- replace the single `{ autogenerate: { directory: 'guide' } }` with explicit groups —
  `{ label: 'Channels', items: [{ autogenerate: { directory: 'guide/channels' } }] }`; or
- rename the directory on disk to `Channels/` (the group label would then be `Channels`, and URLs
  stay `/channels/…` because slugs are lowercased anyway — see [§7](#7-slugs-and-file-naming)).

**Recommendation:** assume the site repo will declare explicit groups. We should not rename
directories in `docs/guide/` for cosmetic sidebar reasons, and we should not promise that
`channels/` will render as "Channels" without site-side config.

### 3d. Collapsed state

`autogenerate.collapsed` (boolean, default `false`) collapses autogenerated subgroups
(<https://starlight.astro.build/guides/sidebar/#autogenerated-links>). As of **0.39.0** this is a
breaking change worth knowing: *"Autogenerated subgroups no longer inherit the `collapsed` value
from their parent group. They are now expanded by default unless explicitly configured with
`autogenerate.collapsed`."* (changelog for
[PR #3618](https://github.com/withastro/starlight/blob/main/packages/starlight/CHANGELOG.md)). This
is a site-config concern, not a content-folder one.

## 4. `index.md` inside a directory

**Source:** [`utils/navigation.ts` L215–L275](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/utils/navigation.ts#L215-L275)

The published documentation does **not** describe this at all. Everything below is from source plus
the shipped snapshot tests.

### In a subdirectory

`treeify()` walks each entry's file path relative to the collection root. Index files are folded
into their own directory node:

```ts
// Handle directory index pages by renaming them to `index`
if (isLeaf && Object.hasOwn(currentNode, part)) {
	currentNode = currentNode[part] as Dir;
	part = 'index';
}
```

— [`navigation.ts` L257–L261](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/utils/navigation.ts#L257-L261)

Result: **`channels/index.md` becomes an ordinary child link inside the `channels` group.** It is
*not* the group's landing page (a `SidebarAutoGroup` has `label` + `entries` and no `href` — the
heading is plain text, not a link), it is not hidden, and it is not automatically labelled
"Overview".

- **Label:** its own `sidebar.label`, falling back to its `title`
  ([`navigation.ts` L285](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/utils/navigation.ts#L285)).
  If we want the "Overview" convention, we write `sidebar: { label: Overview }` ourselves.
- **Position:** first within its group, under default ordering. Its entry `id` (`channels`) is a
  strict prefix of every sibling's `id` (`channels/github`, …), so it always collates first.
- **Slug:** `/channels/` — see [§7](#7-slugs-and-file-naming).

Confirmed by the shipped snapshot: `reference/frontmatter.md` (which Starlight treats identically to
`reference/frontmatter/index.md` — see below) renders as a link labelled `Frontmatter Reference`
with `href: "/reference/frontmatter/"`, as the **first entry inside** a group labelled `frontmatter`
that also contains `Foo` (`/reference/frontmatter/foo/`)
([`__tests__/sidebar/navigation.test.ts`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/__tests__/sidebar/navigation.test.ts);
introduced in [PR #1151](https://github.com/withastro/starlight/pull/1151), whose changelog reads:
*"`src/content/docs/guides.md` and `src/content/docs/guides/example.md` will now both be included and
`src/content/docs/guides.md` is treated in the same way a `src/content/docs/guides/index.md` file
would be."*).

> **Edge case.** The `part = 'index'` rename fires only when the directory node already exists —
> which it does because `treeify` sorts entries deepest-first before building
> ([`navigation.ts` L248](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/utils/navigation.ts#L248)).
> A directory containing *only* an `index.md` and nothing else therefore produces a **plain link**,
> not a group. Not a problem for `channels/` and `deployment/`, which have siblings — but worth
> knowing if a subdirectory is ever reduced to a single page.

### At the collection root

Root `index.md` becomes the site homepage at `/`. Astro's slug generator leaves it as the literal
id `index`, which Starlight normalises to the empty string:

```ts
/*
 * Astro is inconsistent in its `index.md` slug generation. In most cases,
 * `index` is stripped, but in the root of a collection, we get a slug of `index`.
 */
const normalizeIndexSlug = (slug: string) => (slug === 'index' ? '' : slug);
```

— [`utils/routing/index.ts` L19–L23](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/utils/routing/index.ts#L19-L23)

In an autogenerated sidebar it appears as a **top-level link** (not a group), labelled from its
`title`, `href: "/"`, sorted first (empty-string id collates before everything)
([`__tests__/basics/navigation.test.ts`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/__tests__/basics/navigation.test.ts)).

> **Caveat for our layout.** All of the above assumes `docs/guide/` is mounted *at the collection
> root*. If the site mounts it at `src/content/docs/guide/` instead, then `docs/guide/index.md`
> becomes `/guide/` — a child of the `guide` group — not the homepage. The site repo will need its
> own `src/content/docs/index.md` for the homepage in that case.

## 5. Asides in plain `.md`

**Docs:** <https://starlight.astro.build/guides/authoring-content/#asides>

> *"Starlight provides a custom Markdown syntax for rendering asides. Aside blocks are indicated
> using a pair of triple colons `:::` to wrap your content, and can be of type `note`, `tip`,
> `caution` or `danger`."*

**Yes, plain `.md` is fully supported** — that entire guide page is titled "Authoring Content in
Markdown", opens with *"Starlight supports the full range of Markdown syntax in `.md` files"*, and
every aside example is a ```` ```md ```` fence. No `.mdx` required, no component import, no extra
integration.

Why it works: Starlight registers its remark/mdast transforms on Astro's **global markdown
processor** during `astro:config:setup`
([`index.ts`, `applyStarlightMarkdownPlugins(processor, …)`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/index.ts)),
so every `.md`, `.mdx` and `.mdoc` file goes through it. `remark-directive` is a direct dependency
of `@astrojs/starlight`
([`package.json`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/package.json)).

### The complete list of types

Exactly four. Not extensible:

```ts
export const asideVariants = ['note', 'tip', 'caution', 'danger'] as const;
```

— [`integrations/aside-utils.ts` L4](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/integrations/aside-utils.ts#L4)

Default titles are the localised UI strings `Note`, `Tip`, `Caution`, `Danger`
([`__tests__/markdown-processor/asides.test.ts`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/__tests__/markdown-processor/asides.test.ts)).
There is no `info`, `warning`, `important` or `success` aside. (`success` exists only as a *badge*
variant — different feature.)

### Exact syntax

```md
:::note
Plain aside with the default "Note" title.
:::

:::caution[My title]
Custom title in square brackets after the type.
:::

:::tip{icon="heart"}
Custom icon, from Starlight's built-in icon set.
:::

:::tip[Did you know?]{icon="heart"}
Custom title and custom icon together.
:::
```

- Custom title: *"You can specify a custom title for the aside in square brackets following the
  aside type, e.g. `:::tip[Did you know?]`."*
  (<https://starlight.astro.build/guides/authoring-content/#custom-aside-titles>)
- Custom icon: *"in curly brackets following the aside type or custom title, e.g.
  `:::tip{icon="heart"}` or `:::tip[Did you know?]{icon="heart"}`… The icon name must be set to the
  name of one of Starlight's built-in icons."*
  (<https://starlight.astro.build/guides/authoring-content/#custom-aside-icons>) — an invalid icon
  name throws a build error
  ([`aside-utils.ts`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/integrations/aside-utils.ts)).
- Titles may contain inline Markdown (`` :::note[Custom `code` Label] ``) — asserted in
  [`asides.test.ts`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/__tests__/markdown-processor/asides.test.ts).
- Content may contain any Markdown, though *"asides are best suited to short and concise chunks of
  content."* Note the shipped examples put a **blank line before the closing `:::`** when the aside
  contains a fenced code block or a list.

### Configuration needed

**None.** Confirmed by the fact that Starlight pushes the plugins onto the processor itself rather
than asking the user to
([`integrations/markdown-plugins.ts`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/integrations/markdown-plugins.ts)).
One thing to be aware of: that same file warns and silently disables Starlight's markdown transforms
if the site overrides `markdown.processor` with something unsupported — *"Starlight's Markdown
transforms (asides, heading anchor links, RTL code support) won't run on your content."* That is a
site-config risk, not a content-folder one.

> **GitHub-readability note (ours, not the docs').** `:::note` blocks render as literal text on
> GitHub — they are not GitHub's `> [!NOTE]` alert syntax, and the two are mutually exclusive. If
> `docs/guide/` must also read well on GitHub, this is a real cost of converting blockquote callouts
> to asides.

> **Unsupported directive names.** `remark-asides` simply bails on any container directive that is
> not one of the four (`if (!isAsideVariant(variant)) return;`,
> [`remark-asides.ts` L144](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/integrations/remark-asides.ts#L144)).
> The restoration pass that turns unhandled directives back into literal text handles only *text*
> and *leaf* directives (`:foo`, `::foo`), **not** container directives
> ([`remark-asides.ts` L205+](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/integrations/remark-asides.ts#L205)).
> What a stray `:::info` actually renders as is not specified anywhere I could find — do not use one.

## 6. Internal links

### The documented form: absolute site paths

The authoring guide's only example of linking between pages is root-absolute with a trailing slash:

```md
You can [link to another page](/getting-started/).
```

— <https://starlight.astro.build/guides/authoring-content/#inline-styles>

Starlight's own generated links use the same form (`/reference/frontmatter/`, `/channels/github/`),
built by `slugToPathname()`
([`utils/slugs.ts` L50–L58](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/utils/slugs.ts#L50-L58)).

### Relative `./page.md` links are NOT rewritten

I could not find any statement in the Astro docs that Astro resolves relative Markdown-to-Markdown
links, and there is no such feature in the Astro changelog. The Markdown guide
(<https://docs.astro.build/en/guides/markdown-content/>) covers heading IDs, remark/rehype plugins,
and querying collections — and says nothing about relative link rewriting. The only relative-path
resolution Astro documents for Markdown is for **images**, and Starlight repeats exactly that
scoping: *"Relative image paths are also supported for images stored locally in your project."*
(<https://starlight.astro.build/guides/authoring-content/#images>) — images only, not links.

Corroborating primary signals from the Astro org (not documentation, but the repos themselves):
[withastro/astro#5680 "Link Resolution in `index.md` files"](https://github.com/withastro/astro/issues/5680)
and the ["Markdown Enhancements" roadmap discussion #424](https://github.com/withastro/roadmap/discussions/424),
where relative-link resolution is discussed as a *proposal* and the community rehype plugin
[`astro-rehype-relative-markdown-links`](https://github.com/vernak2539/astro-rehype-relative-markdown-links)
is described as a stopgap.

**Verdict:** a `[link](./github.md)` in our Markdown ships to the browser as a literal
`href="./github.md"` and 404s. Every cross-page link in `docs/guide/` must be an absolute site path.

### The GitHub-readability conflict

There is **no official Starlight or Astro guidance** for repositories whose Markdown must render
correctly both on GitHub and in a Starlight site. I searched the Starlight docs and found nothing;
this gap is recorded honestly rather than filled from memory.

The mechanical facts we can act on:

| Link form | Works in Starlight | Works on GitHub |
| --- | --- | --- |
| `/channels/github/` | ✅ (unless the site sets a `base`) | ❌ resolves against `github.com/` |
| `./github.md` | ❌ literal 404 | ✅ |
| `https://docs.example.com/channels/github/` | ✅ | ✅ |

Also note: if the site is ever deployed under a sub-path, Astro's `base` must be prefixed to
absolute links — *"all of your static asset imports and URLs should add the base as a prefix"*
(<https://docs.astro.build/en/reference/configuration-reference/#base>). Root-absolute links written
by hand in Markdown do **not** get the base injected automatically.

**Recommendation:** pick one and state it as a repo rule. Absolute site paths are the only form
Starlight documents, so the honest framing is that `docs/guide/` is *site-first* Markdown that
happens to be browsable on GitHub — not Markdown that is correct in both places.

## 7. Slugs and file naming

**Docs:** <https://starlight.astro.build/guides/pages/#add-pages> — *"Add new pages to your site by
creating `.md` or `.mdx` files in `src/content/docs/`. Use sub-folders to organize your files and to
create multiple path segments."* with the example `hello-world.md` → `example.com/hello-world`,
`reference/faq.md` → `example.com/reference/faq`.

The mechanics live in Astro, since `docsLoader()` delegates to Astro's `glob()` loader with no
custom `generateId`
([`loaders.ts` L15–L63](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/loaders.ts#L15-L63)):

```ts
const slug = rawSlugSegments
	// Slugify each route segment to handle capitalization and spaces.
	.map((segment) => githubSlug(segment))
	.join('/')
	.replace(/\/index$/, '');
```

— [`packages/astro/src/content/utils.ts` L369–L374](https://github.com/withastro/astro/blob/9865d1c03af6d1a1f15c9811858778cc952ca4e4/packages/astro/src/content/utils.ts#L369-L374)

So, precisely:

1. Drop the file extension.
2. Slugify **each path segment independently** with `github-slugger`: lowercase, spaces → hyphens,
   punctuation stripped. (`Example.File.md` → `/examplefile`; documented at
   <https://starlight.astro.build/reference/configuration/#generateid>.)
3. Strip a trailing `/index`. The regex requires a leading slash, so a **root** `index.md` keeps the
   literal id `index` — which Starlight then normalises to `''` → `/`
   ([§4](#4-indexmd-inside-a-directory)).
4. A frontmatter `slug` short-circuits all of the above
   ([§1](#1-frontmatter-schema)); it may contain slashes, producing multi-segment URLs.

Worked examples for our layout, assuming `docs/guide/` is mounted at the collection root:

| File | Entry `id` | URL |
| --- | --- | --- |
| `index.md` | `index` → `''` | `/` |
| `getting-started.md` | `getting-started` | `/getting-started/` |
| `channels/index.md` | `channels` | `/channels/` |
| `channels/github.md` | `channels/github` | `/channels/github/` |
| `deployment/kubernetes.md` | `deployment/kubernetes` | `/deployment/kubernetes/` |
| `README.md` *(if left unrenamed)* | `readme` | `/readme/` ← why the rename matters |

Asserted by Starlight's unit tests: `slugToParam('dir/index') === 'dir'`,
`slugToParam('index') === undefined`, `slugToPathname('') === '/'`
([`__tests__/basics/slugs.test.ts`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/__tests__/basics/slugs.test.ts)).

**File-naming rules for `docs/guide/`:**

- Lowercase, hyphen-separated filenames. Uppercase and spaces work but produce a mismatch between
  the on-disk name (used for `autogenerate.directory` and for sidebar group labels) and the URL
  (sluggified) — see the tie-break asymmetry in [§3b](#3b-how-are-directories-subgroups-ordered).
- Never start a filename with `_`: the loader glob is `**/[^_]*.{…}` and *"File names starting with
  an underscore (`_`) are ignored."*
  (<https://starlight.astro.build/reference/configuration/#docsloader>,
  [`loaders.ts` L57](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/loaders.ts#L57)).
- Directory names become sidebar group labels verbatim — treat them as user-visible text.
- Trailing slashes in generated URLs are a function of the site's Astro `trailingSlash` /
  `build.format` settings, normalised by Starlight's `formatPath`. Not a content-folder concern, but
  hand-written absolute links should match whatever the site uses.

## 8. Importing an external content folder

**This is the weakest link in the whole plan, and it is not a documentation gap — it is a hard
constraint in the code.**

### `docsLoader()` has no `base` option

The documented signature accepts exactly one option, `generateId()`
(<https://starlight.astro.build/reference/configuration/#docsloader>). The docs are explicit about
the location: *"The `docsLoader()` loads local Markdown, MDX, and Markdoc files from the
`src/content/docs/` directory."*

The source confirms the path is computed, not configurable:

```ts
const options: GlobOptions = {
	base: getCollectionPathFromRoot(collection, context.config),
	pattern: `**/[^_]*.{${extensions.join(',')}}`,
};
if (generateId) options.generateId = generateId;
```

— [`loaders.ts` L54–L61](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/loaders.ts#L54-L61)

and `getCollectionPathFromRoot` hard-codes `content/docs` relative to Astro's `srcDir`
([`utils/collection.ts` L25–L37](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/utils/collection.ts#L25-L37)).

### Why it is hard-coded — the maintainers' own comment

This is the most useful primary source on the question, from
[`utils/collection.ts` L3–L19](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/utils/collection.ts#L3-L19):

> *"We still rely on the content collection folder structure to be fixed for now:*
> - *At build time, if the feature is enabled, we get all the last commit dates for each file in the
>   docs folder ahead of time. In the current approach, we cannot know at this time the user-defined
>   content folder path in the integration context as this would only be available from the loader.
>   […]*
> - *Remark plugins get passed down an absolute path to a content file and we need to figure out the
>   language from that path. Without knowing the content folder path, we cannot reliably do so.*
>
> *[…] When user-defined content folder locations are supported, these helper functions should be
> updated to reflect that in one place."*

So: **a custom content folder location is a known, explicitly-unimplemented feature as of 0.41.5.**
Even swapping in a bare Astro `glob({ base: … })` loader would break Git-derived `lastUpdated` dates
and locale detection, both of which resolve paths against `<srcDir>/content/docs/`
([`utils/collection-fs.ts`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/utils/collection-fs.ts)).

### What this means for us

The site repo must make our folder **physically appear** at `src/content/docs/` (or a subdirectory
of it). Mechanisms, in rough order of practicality:

1. **Git submodule** mounted at `src/content/docs/guide/` (or at `src/content/docs/` itself).
2. **Sync/copy step in CI** that clones this repo and copies `docs/guide/` into place before
   `astro build`.
3. **Symlink** into `src/content/docs/`. Untested by me and not documented by Starlight; glob-based
   loaders and file watchers are historically inconsistent about symlinks. Do not assume it works.
4. Changing Astro's `srcDir` — the *only* documented lever, and it moves the whole `src/` tree, not
   just the docs collection. Almost certainly not what anyone wants.

### Constraints this places on `docs/guide/`

- The folder's **internal structure is the URL structure and the sidebar structure**. Wherever it
  gets mounted, the relative layout is preserved verbatim.
- If mounted at `src/content/docs/guide/`, every page gains a `/guide/` URL prefix, `index.md`
  becomes `/guide/` rather than `/`, and `autogenerate.directory` must be `'guide'`,
  `'guide/channels'`, etc. **Decide this before writing any absolute internal links**
  ([§6](#6-internal-links)) — the mount point is baked into every one of them.
- No file may start with `_`.
- Only `.md`/`.mdx`/`.markdown`/`.mdown`/`.mkdn`/`.mkd`/`.mdwn` are picked up (plus `.mdoc` if the
  Markdoc integration is present)
  ([`loaders.ts` L6](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/loaders.ts#L6)).
  Anything else — images, YAML samples, `.go` snippets — is ignored by the loader and must be
  referenced by relative path from a Markdown file (images) or inlined.
- If `lastUpdated` from Git history is enabled on the site, it reads the *site repo's* Git history.
  A copy-based sync would give every page the sync commit's date. A submodule preserves real dates
  only if the site's build has the submodule history available.

## 9. Version and volatility

**Current Starlight: `@astrojs/starlight@0.41.5`, published 2026-07-28**
([releases](https://github.com/withastro/starlight/releases)). It requires `astro: ^7.0.2` and
`@astrojs/markdown-remark: ^7.2.0` as peer dependencies
([`package.json`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/package.json)).
Current Astro is `astro@7.1.6` (2026-07-29).

I verified that `schema.ts`, `loaders.ts` and `utils/navigation.ts` are **byte-identical** between
the `0.41.5` tag and `main` at time of research, so the source citations above describe the released
version, not unreleased work.

### Has the directory-ordering behaviour in §3 shifted between versions?

**No.** I checked `getOrder()` at the `0.28.0`, `0.32.0`, `0.34.0`, `0.36.0` and `0.41.5` tags — the
implementation (`Math.min` over contained routes; `Number.MAX_VALUE` fallback) is character-for-character
unchanged across all five. `sortDirEntries()` likewise. The mechanism dates back to
[PR #359](https://github.com/withastro/starlight/pull/359) (Starlight 0.6.0), which introduced
`sidebar.order` under the changelog headline *"Add support for defining the order of auto-generated
link groups in the sidebar using a frontmatter value"* — note "**groups**", i.e. directory ordering
via contained pages was the *original* intent, not an accident.

Ordering-adjacent changes further back, for completeness
([CHANGELOG](https://github.com/withastro/starlight/blob/main/packages/starlight/CHANGELOG.md)):

- [PR #569](https://github.com/withastro/starlight/pull/569) — *"Use locale when sorting
  autogenerated sidebar entries"* (introduced the `Intl.Collator`).
- [PR #1298](https://github.com/withastro/starlight/pull/1298) — *"Fixes incorrect sorting behavior
  for some autogenerated sidebars"*.
- [PR #1151](https://github.com/withastro/starlight/pull/1151) — made `guides.md` behave like
  `guides/index.md` (the §4 behaviour).
- [PR #2688](https://github.com/withastro/starlight/pull/2688) — Content Layer API fix: *"group names
  would be sluggified"*. **Before this fix, group labels were sluggified; after it they are the raw
  directory name.** Anyone reading older material about Starlight subgroup labels may be describing
  the pre-fix behaviour.
- [PR #2702](https://github.com/withastro/starlight/pull/2702) — Content Layer fix for directories
  with spaces/special characters.

### What *did* change recently (0.39.0, 2026)

Both breaking, both site-config concerns rather than content-folder ones, but they invalidate older
examples:

1. `autogenerate` must now be wrapped in an `items` array. The old form is a build error.
2. Autogenerated subgroups no longer inherit `collapsed` from their parent group.

Both from [PR #3618](https://github.com/withastro/starlight/pull/3618).

### Volatility flags

- **`main` is ahead of the released docs on Markdown processing.** Starlight 0.41.5 already ships a
  pluggable `markdown.processor` (`satteri()` / `unified()`), and warns that Starlight's transforms —
  *asides included* — will not run under an unsupported processor
  ([`integrations/markdown-plugins.ts`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/integrations/markdown-plugins.ts)).
  Nothing here affects our Markdown, but it is a live area of change: if the site repo ever
  customises `markdown.processor`, verify asides still render.
- Starlight's minor versions are still `0.x` and have shipped breaking changes roughly every few
  releases. Pin the site to a known-good version and treat sidebar-shape changes as an expected
  upgrade cost.

## What remains uncertain or unspecified

Recorded as gaps rather than guesses.

1. **`index.md` handling is entirely undocumented.** The published Starlight docs never explain what
   an `index.md` does inside an autogenerated group, at the collection root, or in the sidebar. §4 is
   derived from source and snapshot tests. It is stable across many versions and covered by shipped
   tests, but it is not a documented contract and could change without a changelog entry.

2. **Sidebar tie-breaking is undocumented in prose.** The public docs say only "alphabetical order
   according to the file `id`". That `Intl.Collator` is used (locale-aware, not byte order), that a
   directory's key is its *unsluggified* path while a page's is its *sluggified* id, and that
   unordered pages collapse to `Number.MAX_VALUE` — all source-only.

3. **What an unsupported container directive renders as.** `:::info` is silently ignored by
   `remark-asides` and *not* restored to literal text (only text/leaf directives are). What reaches
   the HTML is not specified in the docs and I did not test it. Avoid non-listed directive names.

4. **Symlinked content directories.** I found no statement, either way, about whether Astro's
   `glob()` loader follows symlinks into `src/content/docs/`. Treat option 3 in §8 as unverified —
   test it before relying on it.

5. **Whether relative-Markdown-link rewriting is planned.** The Astro roadmap discussion is open, not
   accepted; there is no shipped feature and no announced timeline. I am asserting only the *current*
   absence, verified against the Astro 7.1.6 changelog.

6. **Official guidance for dual GitHub/Starlight Markdown.** None found in either docs site. The
   trade-off table in §6 is our own analysis, not a documented recommendation.

7. **How `lastUpdated` behaves for content imported via submodule or CI sync.** Starlight reads Git
   history from the build checkout
   ([`utils/git.ts`](https://github.com/withastro/starlight/blob/5b0690955fa7201f17a5e2d217ae583199a60216/packages/starlight/utils/git.ts)),
   but the interaction with submodules and shallow clones is not documented. If accurate
   last-updated dates matter, either set `lastUpdated` in frontmatter explicitly or verify the
   behaviour on the real pipeline.

8. **Not investigated:** i18n / multi-locale layout (`docs/guide/` is single-language), the
   `<StarlightPage>` component, Markdoc, and Expressive Code code-block syntax beyond noting that it
   exists. Revisit if any of those become relevant.
